# Importing the v1 data

Optional. Do this only if you want the new deployment to start with the
original rocks and accounts instead of empty.

The old passwords were stored in plaintext behind a credential that has been
public since 2024. Treat every one of them as known to strangers. The point of
importing is continuity of the rock registry, not preserving security that was
never there.

---

## 0. Does the data still exist?

Atlas pauses a free M0 cluster after 60 days idle, and eventually deletes a
paused one. This project has been dormant for a while, so check before planning
around it: open the Atlas project and look at the cluster. If it says
**Paused**, resume it; that takes a few minutes and the data is intact. If the
cluster is gone, so is the data, and there is nothing to recover.

---

## 1. Make a temporary export user

Do **not** reuse `hector_admin`. That credential is in the git history of a
public repository; it needs deleting, not using.

In Atlas:

1. **Database Access → Add New Database User**
   - Username `tmp_export`, and use the **Autogenerate Secure Password**
     button rather than typing one.
   - Built-in role: **Only read any database**.
2. **Network Access → Add IP Address → Add Current IP Address**, from whichever
   machine will run the dump.
3. Once the export is done, delete this user and remove the IP entry.

> Do not give it a guessable password. An Atlas cluster answers connections from
> the public internet, and credential pairs like `admin`/`admin` are the first
> thing scanners try; a cluster reachable with one is usually found within hours.
> The account is temporary, but it is temporarily exposed to everybody. Use the
> autogenerated password and paste it into the command below.

While you are in Database Access: delete `hector_admin` now if you have not
already.

---

## 2. Dump

`mongodump` ships inside the official mongo image, so there is nothing to
install locally. Run it on the Pi and you skip the copy step entirely.

```bash
cd ~/HECTOR

docker run --rm --user "$(id -u):$(id -g)" -v "$PWD:/out" mongo:8 mongodump \
  --uri "mongodb+srv://tmp_export:PASSWORD@hector.lnv1yey.mongodb.net/test" \
  --gzip --archive=/out/hector-v1.archive.gz
```

`--user "$(id -u):$(id -g)"` is what makes the output file writable. The mongo
image runs as its own `mongodb` user, which has no write access to your home
directory, and without it the dump ends in
`Failed: open /out/hector-v1.archive.gz: permission denied` after appearing to
work.

> `mongodump`, `mongorestore` and `mongosh` are separate Go and Node binaries
> with none of `mongod`'s ARMv8.2-A requirement, so they run on a Pi 4 even
> though the MongoDB server does not. Only the server is the problem, which is
> why the deployment uses FerretDB but these commands still work.

If the password contains `@`, `:`, `/` or `?`, percent-encode it or the URI
parser will misread it. Autogenerated Atlas passwords are usually safe.

> **Which database?** The old connection string had no database name in the
> path, so Mongoose used the driver default, `test`. Confirm before dumping:
>
> ```bash
> docker run --rm mongo:8 mongosh \
>   "mongodb+srv://tmp_export:PASSWORD@hector.lnv1yey.mongodb.net/" \
>   --quiet --eval 'db.getMongo().getDBNames().forEach(n => print(n))'
> ```
>
> If the collections live somewhere other than `test`, use that name in the
> `--uri` above and in `--nsFrom` below.

Check what you got:

```bash
docker run --rm -v "$PWD:/out" mongo:8 \
  mongorestore --gzip --archive=/out/hector-v1.archive.gz --dryRun -v 2>&1 | grep -i 'found collection'
```

The `WARNING: MongoDB requires ARMv8.2-A or higher` banner is printed by the
image's entrypoint on every invocation, whatever you run. It applies to `mongod`
only. If the command produced output, it worked.

## 3. Restore into FerretDB

If you dumped from your laptop rather than the Pi, copy the archive over first:

```bash
scp hector-v1.archive.gz pi@raspberrypi.local:~/HECTOR/
```

Then on the Pi, in `~/HECTOR`. This runs the tools in a throwaway container
attached to the compose network, so it can reach `ferretdb` by name:

```bash
set -a && source .env && set +a

docker run --rm --network hector_internal -v "$PWD:/in" \
  --entrypoint mongorestore mongo:8 \
  --host ferretdb:27017 \
  --username "$POSTGRES_USER" --password "$POSTGRES_PASSWORD" \
  --authenticationDatabase admin \
  --gzip --archive=/in/hector-v1.archive.gz \
  --nsInclude 'test.*' --nsFrom 'test.*' --nsTo 'hector.*'
```

Two traps in that command, both of which fail quietly:

`docker run`, not `docker compose run`. The latter takes a **service name** from
the compose file, so passing an image gives `no such service: mongo:8`. Plain
`docker run` needs `--network hector_internal` to reach `ferretdb` by name, and
needs `source .env` first because it does not interpolate `.env` the way compose
does.

**No database in the connection.** A database in the URI path acts as `--db`,
and `--db` filters an archive restore to that database. The archive holds
`test.users` and `test.rocks`, so a URI ending `/hector` matches nothing and you
get `0 document(s) restored successfully` with no error. The giveaway is
mongorestore warning that `--db and --collection flags are deprecated for this
use-case` when you never passed either: that is the URI's database talking.
Separate `--host` from the credentials and let `--nsFrom/--nsTo` do the
renaming.

`--nsFrom/--nsTo` is what moves the collections out of the old `test` database
into `hector`, which is where the API looks. Without it the restore succeeds and
the site stays empty, which is a confusing five minutes.

Verify:

```bash
docker compose run --rm --entrypoint mongosh mongo:8 \
  "mongodb://$POSTGRES_USER:$POSTGRES_PASSWORD@ferretdb:27017/hector" --quiet \
  --eval 'print("users:", db.users.countDocuments({}))' \
  --eval 'print("rocks:", db.rocks.countDocuments({}))'
```

## 4. Convert to the v2 shape

The restored documents are still v1 shaped: plaintext `password` fields, no
`createdBy` on rocks, no unique index on `username`. The API will not accept
them as they stand: a v1 user has no `passwordHash`, so login fails for
everyone.

Run it inside the api container, which already has the dependencies. The host
needs no Node toolchain:

```bash
docker compose exec api node backend/scripts/migrate-from-v1.js --dry-run
docker compose exec api node backend/scripts/migrate-from-v1.js
docker compose restart api
```

From a checkout with `npm install` already done, `npm run migrate:v1 -- --dry-run`
does the same thing.

What it does:

| Collection | Change                                                              |
| ---------- | ------------------------------------------------------------------- |
| `users`    | `password` (plaintext) → `passwordHash` (bcrypt), old field removed |
| `users`    | `createdAt` / `updatedAt` backfilled to 2024-05-01                  |
| `rocks`    | missing `owner` key → `owner: null`                                 |
| `rocks`    | `createdBy` backfilled from `owner` where there is one              |
| both       | indexes synced, which is what builds the unique `username` index    |

It is idempotent; running it twice does not re-hash anything.

**Existing passwords keep working.** The v2 complexity rules are enforced at
registration, not at login, so an old password that would be rejected by the
signup form still authenticates fine.

If it reports duplicate usernames it stops before building the unique index and
names them; resolve those by hand in `mongosh` and re-run.

---

## 5. Clean up

```bash
rm hector-v1.archive.gz          # on both machines
```

In Atlas: delete the `tmp_export` user, remove the IP allowlist entry, and, if
you are done with the cluster entirely, terminate it.

That archive holds every account's password in the clear. It should not sit in
your Downloads folder or your shell history.

## Testing this before you trust it

`backend/tests/migration.test.js` seeds a database in the exact v1 shape, runs
the migration, and asserts that an imported account can still sign in with its
original password, that no plaintext survives anywhere, that a released legacy
rock reads as adoptable, and that a second run changes nothing.

```bash
docker compose -f docker-compose.dev.yml up -d
TEST_MONGODB_URI=mongodb://hector:devpassword@localhost:27017/hector-test npm test
```

Note that the suite otherwise runs against real MongoDB, while production runs
FerretDB. Passing tests are necessary but not sufficient. `npm run check:db`
probes the deployed database directly for the operations this codebase depends
on, and is the thing to run after the import:

```bash
docker compose exec api node backend/scripts/check-database.js
```

Rehearsing on a copy first is cheap:

```bash
# restore into a scratch database, migrate, poke at it, drop it
docker compose run --rm --entrypoint mongorestore -v "$PWD:/in" mongo:8 \
  --uri "mongodb://$POSTGRES_USER:$POSTGRES_PASSWORD@ferretdb:27017/rehearsal" \
  --gzip --archive=/in/hector-v1.archive.gz \
  --nsFrom 'test.*' --nsTo 'rehearsal.*'

MONGODB_URI="mongodb://$POSTGRES_USER:$POSTGRES_PASSWORD@localhost:27017/rehearsal" \
  npm run migrate:v1 -- --dry-run
```
