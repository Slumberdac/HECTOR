00

Before you start

Do this first

The repository's git history contains a live MongoDB Atlas connection string. Delete that database user in Atlas now, under Database Access. Rewriting history does not help: the repo has been public, so every clone and fork already has the credential. It has to be rotated, not hidden.

Hardware

A Pi 5, any RAM size; 4 GB is comfortable. The stack runs MongoDB 8, which needs an ARMv8.2-A CPU. The Pi 5's Cortex-A76 has it. A Pi 4's Cortex-A72 does not, and mongod there dies on startup with Illegal instruction (core dumped). If this ever moves to a Pi 4, you need MongoDB 4.4 or a wire-compatible substitute such as FerretDB.

Storage

An SD card works and will eventually wear out under database writes. A USB SSD is the better home for /var/lib/docker. If you stay on SD, take step 06 seriously.

Accounts

A Cloudflare account with your domain's nameservers already pointing at it.

01

Prepare the Pi

Flash 64-bit Raspberry Pi OS Lite with Raspberry Pi Imager, setting hostname, user and SSH key in the imager's advanced options. Then SSH in.

pi · shell 
sudo apt update && sudo apt full-upgrade -y
sudo reboot

# after it comes back, expect aarch64
uname -m

Close off password logins

You are about to run a service that talks to the internet. The Pi itself should not accept password authentication: a guessable password on a box that is up 24/7 is the single most common way a home server gets taken over.

Do these four in order. Turning passwords off before confirming the key works is how people lock themselves out.

1. Prove your key already works

If you gave the Imager a public key in its advanced options it is already in ~/.ssh/authorized_keys on the Pi. Check from your laptop.

laptop · shell 
ssh -o PreferredAuthentications=publickey -o PasswordAuthentication=no pi@raspberrypi.local

A shell means the key is in place; skip to step 2. Permission denied (publickey,password) means it is not, and the trailing password in that list is your reassurance that you can still get in the old way while you fix it.

laptop · shell 
ls -la ~/.ssh/                      # is there an id_ed25519 at all?

# only if you have no key yet:
ssh-keygen -t ed25519 -C "$USER@$(hostname)"

ssh-copy-id -i ~/.ssh/id_ed25519.pub pi@raspberrypi.local   # asks for the Pi password
No identities found

That error from ssh-copy-id means there is no keypair on this machine to copy, not that the Pi refused one. Run the ssh-keygen line first, then re-run the publickey-only check above, and do not continue until it gives you a shell.

Worth putting in ~/.ssh/config while you are here, so the right key is offered and the passphrase is asked for once per session rather than once per connection:

laptop · ~/.ssh/config 
Host pi
    Hostname raspberrypi.local
    User YOUR_USER
    IdentityFile ~/.ssh/id_ed25519
    IdentitiesOnly yes
    AddKeysToAgent yes

2. Write a drop-in, do not edit the main file

Everything below runs on the Pi

Steps 2 to 4 change the SSH server, and the SSH server you want to change is the Pi's. Check your prompt before each one. Hardening your own laptop by mistake is harmless but does nothing for the Pi, and sshd: no hostkeys available from sshd -t is the giveaway: it means that machine has never run an SSH server at all.

pi · shell 
ssh pi                              # if you are not already on it

ls /etc/ssh/sshd_config.d/          # see what is already there

sudo tee /etc/ssh/sshd_config.d/10-hardening.conf >/dev/null <<'EOF'
PasswordAuthentication no
KbdInteractiveAuthentication no
PermitRootLogin no
PubkeyAuthentication yes
EOF
Why editing sshd_config often does nothing

Debian's sshd_config opens with Include /etc/ssh/sshd_config.d/*.conf, and sshd keeps the first value it parses for any directive. Anything in that directory therefore beats what you write further down in the main file. Files there are read in lexical order, so something sorting before 10- would still win; step 3 is what tells you.

KbdInteractiveAuthentication matters as much as PasswordAuthentication. With UsePAM yes, the default, it opens a second, PAM-driven prompt that also accepts a password, so turning off only the first setting leaves the door open.

3. Check the syntax, then the effective result

pi · shell 
sudo sshd -t          # syntax check; silence means valid

sudo sshd -T | grep -Ei '^(passwordauthentication|kbdinteractive|permitrootlogin|pubkeyauthentication)'

# expect exactly:
#   passwordauthentication no
#   kbdinteractiveauthentication no
#   permitrootlogin no
#   pubkeyauthentication yes

sshd -T prints the configuration sshd will actually use, after every include and override. It is the only output worth trusting.

4. Restart, and test from a second terminal

pi · shell 
sudo systemctl restart ssh

# if that reports no such unit, the system uses socket activation:
#   sudo systemctl restart ssh.socket
Keep the first session open

An existing session survives an sshd restart, so it stays as your way back in if the new config is wrong. Open a new terminal, connect again, and only close the first one once the second has worked.

If you do lock yourself out: attach a keyboard and monitor, or shut the Pi down, put the card in another Linux machine, mount the ext4 partition and delete 10-hardening.conf. Tedious, never fatal.

Optional, if you have a hardware key: ssh-keygen -t ed25519-sk makes a key whose private half cannot leave the token, so a copy of your laptop's disk is not enough to log into the Pi. Needs OpenSSH 8.2 or newer at both ends, which Pi OS has.

Automatic patches

Nobody patches a Pi they cannot see.

pi · shell 
sudo apt install -y unattended-upgrades
sudo dpkg-reconfigure -plow unattended-upgrades

Swap

MongoDB dislikes running out of memory. On a Pi 5 with 8 GB this is precautionary rather than necessary; with 4 GB it is cheap insurance. Look at what you already have first, because Raspberry Pi OS has used three different swap mechanisms over the years.

pi · shell 
free -h
swapon --show
If you see /dev/zram0, stop here

That image uses zram, compressed RAM rather than a file on the card. It does not add capacity the way a swapfile does, but it is far kinder to an SD card, and for this workload it is the better arrangement. Leave it alone and go to step 02.

pi · shell 
# older images, dphys-swapfile
sudo dphys-swapfile swapoff
sudo sed -i 's/^CONF_SWAPSIZE=.*/CONF_SWAPSIZE=2048/' /etc/dphys-swapfile
sudo dphys-swapfile setup && sudo dphys-swapfile swapon

# newer images, rpi-swap: drop-in config, applied on reboot
sudo mkdir -p /etc/rpi/swap.conf.d
man swap.conf              # the keys your version accepts
sudo reboot

dphys-swapfile: command not found simply means your image uses one of the others. It is a branch to take, not an error to fix.

02

Install Docker

pi · shell 
curl -fsSL https://get.docker.com | sudo sh
sudo usermod -aG docker "$USER"
newgrp docker            # or log out and back in
docker run --rm hello-world

Cap the log driver so logs cannot fill the card.

pi · shell 
sudo mkdir -p /etc/docker
echo '{"log-driver":"json-file","log-opts":{"max-size":"10m","max-file":"3"}}' \
  | sudo tee /etc/docker/daemon.json
sudo systemctl restart docker
03

Code and secrets

pi · shell 
git clone https://github.com/Slumberdac/HECTOR.git
cd HECTOR
cp .env.example .env

# three distinct secrets
for n in MONGO_ROOT_PASSWORD MONGO_APP_PASSWORD JWT_SECRET; do
  echo "$n=$(openssl rand -base64 36 | tr -d '/+=' | head -c 48)"
done

chmod 600 .env

Paste those three lines into .env and fill in the two usernames. Leave CLOUDFLARE_TUNNEL_TOKEN empty; step 04 produces it.

One-shot value

MONGO_APP_PASSWORD is consumed once, on the very first boot, by ops/mongo-init/01-create-app-user.js. Changing it later has no effect on an existing volume; you would have to change the password inside mongo, or destroy the volume and restore from a backup.

04

Create the tunnel

In the Cloudflare dashboard: Zero Trust → Networks → Tunnels → Create a tunnel → Cloudflared. Name it hector-pi.

The install screen shows a docker run command. You do not need to run it. Copy only the token out of it and put it in .env:

pi · .env 
CLOUDFLARE_TUNNEL_TOKEN=eyJhIjoi…
Treat as a password

That token can publish services from your network. Anyone holding it can point a hostname on your domain at something of their choosing.

Then on the tunnel's Public Hostname tab, add a route:

Field Value
Subdomain blank, or hector
Domain your domain
Path blank
Type HTTP
URL web:8080

web:8080 is the container name and port on the compose network; cloudflared resolves it over Docker's internal DNS, so nothing is exposed to your LAN. The DNS record is created for you, since the zone is already on Cloudflare. For www as well, add a second public hostname pointing at the same web:8080.

05

First deploy

pi · ~/HECTOR 
docker compose up -d --build

docker compose ps          # four services, api and web healthy
docker compose logs -f api # expect "Connected to MongoDB"

curl -fsS http://127.0.0.1:8080/healthz
curl -fsS http://127.0.0.1:8080/api/v1/rocks

The first build takes a few minutes on a Pi. Then visit your domain: register an account, add a companion, sign out, sign back in.

Confirm the fixes are live

Three checks that the old failure modes are actually closed on the running deployment, not just in the source.

laptop · shell 
# 1. no password material in the user registry
curl -s https://your-domain/api/v1/users | grep -i password || echo "clean"

# 2. anonymous callers cannot create, expect 401
curl -s -o /dev/null -w '%{http_code}\n' -X POST https://your-domain/api/v1/rocks \
  -H 'Content-Type: application/json' -d '{"name":"x"}'

# 3. the session cookie is httpOnly + Secure + SameSite=Strict
curl -si -X POST https://your-domain/api/v1/auth/login \
  -H 'Content-Type: application/json' \
  -d '{"username":"you","password":"…"}' | grep -i set-cookie
05b

Import the old data

Optional, and only if you want the registry to open with the original rocks and accounts rather than empty. Skip straight to step 06 otherwise.

Check it still exists first

Atlas pauses a free M0 cluster after 60 days idle and eventually deletes a paused one. Open the Atlas project: if it says Paused, resume it and the data is intact. If the cluster is gone, so is the data.

A temporary export user

Do not reuse hector_admin; that one needs deleting, not using. In Atlas: Database Access → Add New Database User, named tmp_export, role Only read any database. Then Network Access → Add Current IP Address. Remove both when you are finished.

Dump

mongodump ships inside the official mongo image, so there is nothing to install.

laptop · shell 
# the old URI had no database in the path, so Mongoose used "test"
docker run --rm -v "$PWD:/out" mongo:8 mongodump \
  --uri "mongodb+srv://tmp_export:PASSWORD@hector.lnv1yey.mongodb.net/test" \
  --gzip --archive=/out/hector-v1.archive.gz

scp hector-v1.archive.gz pi@raspberrypi.local:~/HECTOR/

Restore and convert

pi · ~/HECTOR 
docker compose cp hector-v1.archive.gz mongo:/tmp/v1.gz

docker compose exec mongo mongorestore \
  --username "$MONGO_ROOT_USERNAME" --password "$MONGO_ROOT_PASSWORD" \
  --authenticationDatabase admin \
  --gzip --archive=/tmp/v1.gz \
  --nsFrom 'test.*' --nsTo 'hector.*'

# bcrypt the plaintext passwords, normalise owners, build the index
npm run migrate:v1 -- --dry-run
npm run migrate:v1
docker compose restart api
The easy thing to miss

--nsFrom/--nsTo is what moves the collections out of the old test database into hector, which is where the API looks. Without it the restore reports success and the site stays empty.

Old passwords keep working: the v2 complexity rules are enforced at registration, not at login. Then delete the archive from both machines and remove the tmp_export user; that file holds every account's password in the clear.

Full procedure, including how to rehearse it on a scratch database first, is in docs/MIGRATION.md.

06

Backups

An SD card will fail eventually. Assume it.

pi · crontab -e 
15 3 * * *  /home/YOUR_USER/HECTOR/ops/backup.sh >> /home/YOUR_USER/HECTOR/ops/backup.log 2>&1

ops/backup.sh writes a compressed mongodump archive per night and prunes anything older than 30 days. Backups on the same card as the data are not backups; pull them somewhere else:

laptop · shell 
rsync -av pi@raspberrypi.local:HECTOR/ops/backups/ ~/hector-backups/

Restoring

pi · ~/HECTOR 
docker compose cp ops/backups/hector-DATE.archive.gz mongo:/tmp/restore.gz
docker compose exec mongo mongorestore \
  --username "$MONGO_ROOT_USERNAME" --password "$MONGO_ROOT_PASSWORD" \
  --authenticationDatabase admin --gzip --archive=/tmp/restore.gz --drop
Worth doing today

Run a restore once now, while nothing depends on it working. An untested backup is a guess.

07

Updating

pi · ~/HECTOR 
# your code
git pull
docker compose up -d --build
docker image prune -f

# base images: mongo, caddy, cloudflared
docker compose pull
docker compose up -d

Do a mongo major-version bump deliberately, not as a side effect of pull. Read the release notes, take a backup, then move.

08

Optional hardening

Where What Why
WAF → Rate limiting 100 req/min per IP on /api/* Abuse is stopped at Cloudflare's edge and never reaches your home connection
Security → Bots Bot Fight Mode Free, removes most background noise
Zero Trust → Access Policy on any admin surface Identity-provider gating with no code, if you ever add one
Any uptime monitor GET /healthz Returns 503 when the database is down

What listens where, when you are done

Container Listens Reachable from
mongo 27017 api only
api 5000 web only
web 8080 cloudflared, plus 127.0.0.1 on the Pi
cloudflared nothing inbound nothing

Only web publishes a host port, and only on loopback for debugging over SSH. Everything the public reaches arrives through the tunnel.

Troubleshooting

mongod exits immediately with “Illegal instruction”

You are on a Pi 4 or older. MongoDB 5.0+ requires ARMv8.2-A; the Cortex-A72 is ARMv8.0-A. Pin mongo:4.4 (end of life) or move to FerretDB, which speaks the MongoDB wire protocol over Postgres and needs no Mongoose changes.

docker compose up says “set MONGO_APP_PASSWORD in .env”

Working as intended. The compose file uses ${VAR:?} so a missing secret fails loudly at startup rather than quietly starting an unauthenticated database. Fill in .env.

API logs MongoServerError: Authentication failed

MONGO_APP_PASSWORD changed after the volume was initialised. The init script only runs on an empty data directory. Either set the password inside mongo, or docker compose down -v, which destroys the data, and restore from backup.

Cloudflare shows error 502

cloudflared reached the tunnel but not the origin. Check the public hostname is http://web:8080. localhost:8080 will not work: from inside the cloudflared container, localhost is the cloudflared container.

Cloudflare shows error 1033

The connector is not running. docker compose logs cloudflared, usually a bad or revoked token.

The site loads but every API call 502s

The api container is unhealthy. docker compose logs api. Most often the config validator rejected an environment variable and the process exited; the message names the variable.

Sign-in works, then you are immediately signed out

The session cookie is Secure, so it is only sent over HTTPS. Reaching the site over plain HTTP, for example directly at http://pi-ip:8080, does exactly this. Use the real domain.

Builds run out of memory on the Pi

Increase swap (step 01), or build on your laptop with docker buildx build --platform linux/arm64 and push the images to a registry.
